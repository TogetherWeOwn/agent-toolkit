# Shared GitHub App protocol helpers

Internal package 0.1.0; GitHub REST API `2022-11-28`. Used independently inside each credential-bearing plugin worker. No ambient credentials, environment access, logging, persistent state or token-return tool.

REA/provenance: extracted and adapted from the existing [GitHub upstream watcher](https://github.com/TogetherWeOwn/paperclip-plugin-github-upstream) App JWT and fixed-origin REST implementation. The RS256 JWT retains its 60-second skew and 600-second signed lifetime. That watcher's empty-permissions mint, PAT fallback, arbitrary GraphQL helper and installation-token cache are **not** appropriate for this broker and are not carried forward. Short fresh-data caching is implemented at the authorized/projection layer instead (no conditional headers or ETag revalidation); `withInstallationToken` mints only for uncached broker reads. It attempts revocation in `finally` whenever the successful mint contains a recoverable nonempty token string, including rejected token shapes. Unparseable/missing token responses and credentials unsafe for an HTTP header cannot be revoked locally; provider expiry bounds those residual cases.

This package supplies protocol mechanics, not caller authorization. `mintScope` refuses missing repository IDs or permissions, multiple repositories, empty or unsupported permissions and all write permissions before signing or HTTP. The caller supplies a trusted transport, allowlisted repository/operation and safe response observer. `request` always fixes `https://api.github.com`, refuses redirects and bounds the returned body, but relies on the native transport's separately verified no-follow/deadline/DNS-pinning contract. The plugin's acceptance record covers that integration.

An ambiguous failed mint can create a server-side token that the worker never receives; no blind retry is performed. Provider expiry bounds that residual lifetime. A revoke failure is always a fixed error, not unqualified success. The temporary SDK null-body mitigation accepts only a typed fixed-DELETE boundary failure followed by one same-token 401 `Bad credentials` verification with an observer-validated, scrubbed request ID. The observer returns that safe ID or `undefined`; it must never return an unvalidated header. Cleanup evidence distinguishes a directly observed 204 from probe-verified token rejection and explicitly records the inaccessible DELETE request ID. See the broker runbook for retirement after verified compatible adoption of a published SDK fix. No secret-memory zeroization guarantee is made.
