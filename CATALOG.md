All candidates require a separate trusted credential-execution boundary: no ambient agent credential delivery or alternate secret/environment/filesystem access path, no untrusted code execution beside credentials, and trusted tenant/agent/project/task audience plus resource ownership validation. Use many small tools per provider credential trust boundary, separating production from test trust where needed. No generic HTTP, SQL, shell, management, credential-return or token-creation API is in scope. Deny unknown operations and arguments at runtime. Resolve credentials only after authorization at call time; never return or log them. Require safe per-attempt audit records, synthetic canary-redaction/refusal tests, hard TTL/resource/spend caps and independent durable cleanup where applicable. High-impact approval binds the exact canonical action, target and artifact and must be revalidated at execution. Security acceptance precedes operator installation/configuration; catalog inclusion grants no permission.

Existing cf-test-env scoped-token delegation is a separate exposure class, not certified strict no-credential-output brokerage. Distinguish credential-vending launchers from exact-action brokerage: authentication alone does not prove command-level authorization. Managed GitHub operation/tenant/approval guarantees must be verified against source and the target host version; the GitHub upstream watcher is an adjacent sync/audit plugin, not that broker. A post-hoc audit is not pre-call authorization.

REA angle: reuse shipped broker policy/fixture patterns and provider-native scoping first; verify target-host plugin identity, isolation and governance behavior from source/contracts. Route unresolved protocol questions for offline specification work, not production probing.

## Demand ranking protocol

The Security Engineer's credential risk sweep is an additional input to this demand-ranked backlog. Incorporate its evidenced credential ceilings, excessive permissions, affected workflows and native-scope alternatives alongside the Product and Infrastructure reports. Sanitized sweep requirements are incorporated above as risk-derived or conditional candidates; no private credential inventory or effective-scope certification is published. Do not promote them to measured demand. Security urgency and observed workflow demand should be recorded separately; a sweep finding is not an approval to expand access or install a broker.

Request concrete examples from product and infrastructure leads: service and workflow, who is blocked, currently missing operation, coarse credential permission, frequency in the last 30 days, number of agents/projects affected, urgency, and a source that can be summarized publicly. A response of “no current pain” is useful and must not be inflated into demand.

Rank confirmed blockers first, then repeated manual operator work, then speculative candidates. Within a tier, use measured frequency and breadth of users; if evidence is absent, keep candidates tied/unranked rather than inventing a score. Record dates and sanitised rationale here; private task IDs, deployment details, credentials and internal host data stay out of the public catalog.

## Admission and maintenance

A catalog entry includes source/version, maintainer role, exposure class (pure broker versus delegated credential), verified operations, principal/resource boundaries, test evidence, target governance coverage and acceptance status. New packages must satisfy [STANDARD.md](STANDARD.md). Security acceptance binds the exact artifact and configuration envelope, not the provider name. Operator installation/configuration follows acceptance; no catalog row itself grants access.

REA angle: compare shipped Cloudflare scoping/fixtures and managed GitHub broker behavior with provider-native permissions before implementing candidates. Prefer an existing narrow mechanism to a new broker. Do not infer guarantees from a tool name or an available connection.

## GitHub broker implementation candidate

[`plugins/github-broker`](plugins/github-broker/README.md), version 0.2.0, adds eight read-only tool handlers plus one allowlisted staging workflow-dispatch write (`github.workflow_dispatch_allowlisted`, devops profile only, TWO-5764 tier 1), with per-agent/project/workspace policy and repository-scoped GitHub App minting per uncached call. It reuses core 0.1.0 and the extracted [`packages/github`](packages/github/README.md) protocol helpers. Maintainer: agent-toolkit maintainers. This is **not installed or security-accepted**; Actions evidence, independent Security and cryptography reviews, exact-artifact host/governance verification and sandbox QA remain gates. The dispatch write additionally requires DevOps confirmation of the live workflow inputs and Security Engineer acceptance before enablement. No operator-created or persistent credential creation, interim broad-key exception, existing-grant removal or other write capability is authorized; internal ephemeral installation-token minting per uncached call is the documented runtime behavior. See its [threat model](plugins/github-broker/THREAT-MODEL.md) and [pending acceptance record](plugins/github-broker/ACCEPTANCE.md).

## Implementation and evidence limits

This repository supplies shared core policy primitives, adapter contracts, offline fixtures and an unaccepted GitHub plugin implementation candidate. No operational provider installation, production state store, scheduler or installation acceptance is supplied.

Source inspection supports reuse assessment, not a live vulnerability finding, provider permission canary or Security acceptance. Existing Cloudflare ownership/project/ledger and cleanup patterns are useful, but legacy token output, unknown-argument handling and tracked-environment concurrency do not establish strict no-credential-output, closed-schema or spend-cap conformance. Managed GitHub acquisition controls do not prove semantic command authorization. Runtime plugin approval routing exists in inspected source; connected-MCP target snapshots do not establish generic-plugin provider-target/artifact binding. Verify the exact native invocation, worker/secret isolation and alternate credential-access paths on the target host before acceptance. No production probing or credential changes are authorized by this catalog.
