# GitHub read broker

Version 0.1.0. Maintainer: agent-toolkit maintainers. **Enablement blocked by host compatibility and renewed acceptance.** SDK/host baseline: `@paperclipai/plugin-sdk@2026.1023.0`, Node 24.11+, GitHub REST `2022-11-28`, core 0.1.0 and shared GitHub helpers 0.1.0. See [ACCEPTANCE.md](ACCEPTANCE.md) and [THREAT-MODEL.md](THREAT-MODEL.md).

## Known host compatibility blockers

**Do not enable until the temporary mitigation below is implemented, verified and independently accepted on the exact artifact/host.** Pinned SDK `2026.1023.0` reconstructs HTTP replies with `new Response(result.body, ...)`. An empty-string body throws for null-body statuses 204/205/304, losing the response status and headers at the plugin boundary. `test/sdk-http.test.mjs` exercises the actual published SDK over RPC with empty-string and null-body controls. It is a defect reproduction, not a fix or a green enablement gate. Do not bypass the mint pause by restarting the worker.

### Accepted temporary mitigation contract (verification pending)

The implementation below is a temporary mitigation, **not operational acceptance**. Its offline regression coverage is in `test/revocation.test.mjs`, `test/sdk-http.test.mjs` and `test/broker.test.mjs`; exact-head Actions and independent artifact/host verification remain required.

- The plugin transport will recognize only a `TypeError` whose message equals exactly `Response constructor: Invalid response status code 204`, and only when handling the fixed `DELETE https://api.github.com/installation/token`. It must expose a typed failure to shared cleanup, never fabricate an HTTP status, response, header or request ID. All other URLs, methods, error types/messages and 205/304 errors stay failures.
- Only that typed failure permits the first `GET https://api.github.com/installation/repositories?per_page=1`, using the identical installation token and the same `ctx.http.fetch` transport and IPC limits. A real DELETE 204 remains the normal `revoked` path, with zero probes. No second DELETE, remint, alternate transport or broader token is allowed.
- A completed first **200 with a valid sanitized request ID**, after successful observer handling, permits **one** additional identical-token GET. Capture monotonic `t0` immediately after the SDK fetch resolves, before body consumption or validation, and carry it only as internal transport metadata; the immutable deadline is `D=t0+2000 ms`. Dispatch the second no earlier than `t0+250 ms`; classification/observer work, delay, FIFO waiting, dispatch and body/evidence consumption all count. Check before admission, after FIFO wake, inside the action microtask before RPC and after completion/classification. Equality or expiry fails terminally; no late completion changes evidence, audit, output or cache. The delay is not proof of propagation lag or a promise of recovery.
- Only status **401**, a JSON **object** whose `message` is exactly `Bad credentials`, and a sanitized valid `x-github-request-id` counts as `revoked_verified_by_probe`; the second must qualify strictly before D. This establishes **rejection at verification time**, not causal DELETE success or global rejection across provider replicas. A first 200 remains contradictory-time evidence. Every ineligible first response, failed observer, persistent second 200, malformed evidence, transport/capacity error or expired window keeps `mint.revoke_failed`, the 3660-second pause and no result/cache. Audit outage also fails closed; in the recovery branch it retains the pause even after a qualifying second 401, before attempting denial audit.
- Audit adds a `revocation` field, distinct from the call's overall outcome. Its successful cleanup `outcome` is `revoked` or `revoked_verified_by_probe`. The fallback records `deleteRequestId: null`, `unavailableReason: "sdk_null_body"`, and a valid sanitized `probeRequestId`; the unavailable DELETE evidence must never be invented or replaced with the probe ID. Normal cleanup records the actual sanitized DELETE request ID when available. Probe body/error text and credentials are not logged.
- Fallback audit also records `probeStatus` (the validated numeric response exposed to shared cleanup, or null) and fixed `probeResult`: `unavailable`, `unexpected_status`, `invalid_json`, `unexpected_body`, or `bad_credentials`. Only 401 bodies are classified; other response bodies are never parsed for diagnostics. Status/classification are retained before the rate-limit observer can throw. `bad_credentials` alone is not cleanup success: the 401 and sanitized request-ID requirements still apply. Null/`unavailable` means the request helper exposed no validated response (including transport/SDK/response-validation failure), not an inferred provider status. Raw bodies, headers and exception text remain excluded. The fallback additionally retains at most two ordered immutable `probes` records (attempt, status, sanitized ID, fixed result), `secondDispatched` and a finite `terminalReason`. An unattempted/expired attempt has null status/ID, never a fabricated response. Frozen terminal evidence ignores late replies. These diagnostics cannot recover a historical response or establish propagation lag.
- Reserve **`N+5` HTTP requests before secret resolution**: mint + immutable repository-ID verification + `N` data reads + DELETE + two possible probes. For `checks_get`, `N=3`, so reserve eight; single-read tools reserve six. Unused reservations are not refunded. The fallback remains subject to the same host budget; inability to obtain probe evidence is a cleanup failure, not an exemption.
- Disable conditional revalidation: **no `If-None-Match`, no retained ETag revalidation**. Keep only the 10-second fresh projected-data cache, still authorization-checked on every hit. After freshness expires, perform an unconditional read. An unsolicited 304 fails closed and never revives cached data; 205 has no supported success path.

The complete [endpoint/null-body inventory](THREAT-MODEL.md#endpoint-and-null-body-inventory) covers shared lifecycle calls and all eight tools. No general empty-body workaround or null-status success inference is authorized.

Remove the fallback only after a compatible **published** SDK containing [upstream #17282](https://github.com/paperclipai/paperclip/pull/17282) is adopted and the actual installed worker is shown to resolve that version. Flip the real-RPC regression from reproducing the defect to asserting preserved status/request ID for null-body replies, delete both probes, delayed recovery and probe-specific handling (retain general uncertain-slot safety), then obtain normal exact-head CI, independent review and installed-host acceptance. A merged upstream change, lockfile edit or null-body fake alone is insufficient.

The host's plugin result envelope also needs correct MCP projection: a string `content`, record `data`, and native `error` from this plugin must reach the MCP client without a null `structuredContent` or loss of failure status. Until a containing stable host release is installed and verified, use the [run-scoped REST client](#run-scoped-rest-client) instead. This is an alternative acceptance path, not a core/SDK patch or proof of successful broker reads. The related host repair is [paperclipai/paperclip#10317](https://github.com/paperclipai/paperclip/pull/10317); upstream merge alone does not retire REST.

Tool discovery uses flat root object schemas. Mode-specific required/forbidden combinations remain enforced by the closed runtime validators before secret access. Omit unused fields rather than supplying null. `test/discovery.test.mjs` checks metadata for all eight registered tools and negative variant combinations; actual agent-session visibility still requires a new canary.

## Tools

Each tool requires `issueId`, `workspaceId`, and numeric `repoId`. These are selectors, not identity assertions: the host is trusted to authenticate and supply the gateway principal (the plugin schema-validates it, not its provenance). The broker verifies the issue's company/project/assignee/current run/active status, its explicit workspace, that workspace's exact repository URL, the board policy's numeric repository ID, and GitHub's repository ID. Unknown fields fail closed.

| Tool | Additional required arguments | Returned subset |
| --- | --- | --- |
| `github.repo_read` | `mode=file, ref, path`; `mode=tree, ref`; `mode=ref, ref`; or `mode=compare, base, head` | UTF-8 file text, shallow tree, ref SHA/type, or bounded compare |
| `github.pr_list` | `state=open/closed/all, page, perPage` | PR metadata, body, base/head refs and SHAs |
| `github.pr_get` | `number` | One PR's metadata, body and head/base |
| `github.pr_files` | `number, page, perPage` | File names/status/counts/patches |
| `github.checks_get` | `sha, page, perPage` | Check runs, producer-qualified commit statuses and workflow runs for a full 40-character SHA |
| `github.rulesets_get` | `page, perPage` OR `rulesetId` | Inherited/repository summaries, or enforcement/rules with explicit incomplete-parameter markers; no bypass actors |
| `github.actions_runs_list` | `page, perPage` | Run metadata only, no logs/artifacts |
| `github.issue_read` | `number` | Issue metadata and body, no comments |

Pagination is explicit (pages 1–100, at most 100 items). Results are bounded evidence, not a claim of complete history or successful checks. File output is at most 128 KiB; binary files and oversized responses are refused. Unpaginated tree/compare-file arrays are clipped to 100 entries with `truncated`/`filesTruncated` markers; provider tree truncation is preserved. Neither listing rulesets nor the supported detail projection establishes all effective branch protections; rule details omit conditions and explicitly mark unsupported parameters.

`checks_get` returns both projected pages and a unified `signals` list. Each signal has `producerTrusted` and `passing`; upstream success alone never means passing. Actions check-runs for known CI contexts require App 15368; Devin checks require App 811515. The aggregate `CodeQL` context requires GitHub Advanced Security App 57789 (verified from the repository's real check-run payload); Actions `Analyze (...)` jobs remain App 15368. Commit statuses require creator `devin-ai-integration[bot]` of type `Bot` for `Devin Review`; the combined-status endpoint omits creators, so the broker instead reads newest-first `/statuses`. Only the first status per context on page 1 is current. Check runs are current only for unique context names in a complete first-page collection (`checksComplete`); duplicate names across suites or incomplete/later pages are ambiguous evidence and never pass. The broker does not guess rerun/workflow precedence from IDs or timestamps. Older status duplicates, unknown contexts, missing/unexpected producers and mismatched check SHAs do not pass. `producerTrusted` proves only the producer App or status creator, not the identity of a workflow/job; a same-repository workflow can reuse a CI context name. Workflow runs and empty/queued check suites never synthesize a signal. This is not an overall merge verdict: callers must obtain all required contexts and effective rules separately.

All tools are **read** operations. There is no REST/GraphQL/shell proxy, Git command, workflow write, PR write/merge/review, Actions write, artifact/log download or credential-return tool. Native names are additionally namespaced by the plugin host. SDK `error` is populated on every failure. The REST client inspects it independently of HTTP status; see the baseline host's wrapper-level invocation-status limitation below.

## Run-scoped REST client

`src/client.ts` is a temporary caller for the shipped `POST /api/plugins/tools/execute` agent branch, not a new tool or credential broker. Build/package it through the same reviewed Actions artifact. From a checked-out running task, with the runtime's existing `PAPERCLIP_API_URL`, `PAPERCLIP_API_KEY`, `PAPERCLIP_COMPANY_ID`, `PAPERCLIP_AGENT_ID`, `PAPERCLIP_RUN_ID`, `PAPERCLIP_TASK_ID` and `PAPERCLIP_WORKSPACE_ID` environment:

```sh
node plugins/github-broker/dist/plugins/github-broker/src/client.js \
  '<verified-project-uuid>' github.pr_get <<'JSON'
{"issueId":"<current-task-uuid>","workspaceId":"<selected-workspace-uuid>","repoId":101,"number":1}
JSON
```

Use the **verified native project's UUID**, not a guessed primary project or another task's context. In an installed package, the entry is `dist/plugins/github-broker/src/client.js` relative to its package root. The arguments shown are non-secret placeholders; never place a key, token or authorization header in argv, stdin, files or comments. Do not call before Operator enablement and caller acceptance. Other tools use the same names/closed arguments in the [table](#tools), including both multi-mode reads. No raw URL, plugin selector, identity override or approval flag is supported.

- The client accepts only the current task/workspace selectors and eight existing read schemas/path validators. It constructs `tool: "togetherweown.github-broker:<github.tool>"`, `parameters`, and `runContext: {companyId, agentId, runId, projectId}`. The tool prefix is the **plugin key**, not its database UUID or MCP-normalized name. The run header and bearer come only from the runtime environment. Structural JWT claim/expiry checks reject absent/mismatched run identity and non-JWT board keys early; **only the server verifies signatures and authenticates the live run**. This is not a new authorization authority.
- The injected API URL is a trusted runtime binding: HTTPS, or loopback HTTP for the local runtime. Only root or `/api` bases are accepted; userinfo, query/fragment, other paths, redirects and all retries are refused. Input is capped at 16 KiB with a 5-second stdin deadline; one POST and its response share a 45-second abort deadline and a 4-MiB wire-response bound. That finite wire budget accounts for three 256-KiB projected pages, derived signals, duplicate `content`/`data` and JSON string escaping; it does not raise the broker's per-page or upstream HTTP limits. A timeout may leave the server request running: do not blindly repeat it. No App key or GitHub installation token is resolved by this client.
- The agent route retains the host's company/agent/run/project scope validation, policy/approval/rate controls, content redaction and invocation/audit recording before dispatching the unchanged broker. Broker issue/workspace/profile/repository checks, cleanup probe, `N+5` reservation, mint pause and fresh-cache authorization remain authoritative and unchanged. No board branch, gateway-session creation, core patch or alternate GitHub channel is used.
- A valid HTTP 200 wrapper must identify this plugin and the requested tool, and contain a record `result.data` with boolean `ok`. Success must also match operation/repository. The client returns `{ok, status, data}`; nested `result.error` or `data.ok: false` is **failure**, with the rule and projected denial data preserved. It never treats null, replay summaries, malformed wrappers or HTTP errors as successful reads. All failures exit nonzero; raw host bodies, exception messages and bearer reflections are not printed. Successful repository text remains untrusted data, not instructions.
- HTTP failures retain status and bounded `reasonCode`; approval failures retain native invocation/action/interaction/issue references and argument hash, without confirming or retrying. Stop on `approval_required`, follow the native interaction and inspect the recorded execution outcome on continuation. The baseline host's approved-action executor can return `approved_execution_unsupported` for plugins; approval is not proof of execution and there is no client confirmation override. Route that actual prerequisite through the existing approval owner if encountered.
- **Host audit limitation:** baseline 2026.1023.0 records the returned plugin wrapper as a succeeded gateway invocation even when its nested SDK result has an error. The client corrects the caller's result/exit, not that host row. Preserve both native policy/invocation evidence and the broker's distinct denial/outcome activity record; do not cite the host row alone as a successful broker read. Exact-host Security/Crypto acceptance must assess this limitation. Offline client fixtures are not per-caller live authorization or durable-audit acceptance.

Retirement: install a stable host release containing [the envelope/error correction](https://github.com/paperclipai/paperclip/pull/10317), then QA verifies fresh-session MCP output/error propagation and the same caller/sandbox controls. Switch callers back and delete this client/fixtures/runbook only after that passes. No upstream merge prerequisite is imposed on REST acceptance.

## Board-only configuration

Configuration is read through the native plugin configuration API and is never accepted from tool arguments or changed by this plugin. The board/operator binds a company secret at `privateKeySecretRef`, with `secrets.read-ref` granted only to this plugin. A secret binding is an object, never a raw string or value.

Synthetic example (replace all identifiers with verified native metadata):

```json
{
  "appId": 42,
  "installationId": 99,
  "privateKeySecretRef": { "type": "secret_ref", "secretId": "secret-one" },
  "policy": {
    "version": 1,
    "revision": 1,
    "companyId": "company-one",
    "repositories": [{ "id": 101, "owner": "synthetic-org", "name": "sandbox", "projectId": "project-one", "workspaceId": "workspace-one" }],
    "agents": [{ "agentId": "agent-one", "profile": "reviewer-read", "identityLane": "app", "repositoryIds": [101] }]
  }
}
```

Profiles `builder`, `lead`, `reviewer-read` and `release` explicitly allow the eight reads on selected repositories. `coordinator-read` excludes file/tree/compare reads and PR patches. `none`, absent agents and empty repository grants deny everything. No write privileges are implied by the profile names. Arrays cap at 32 entries. Board sections validate exact own data descriptors and compose bounded core leaf schemas, supporting the complete 32-repository/32-agent matrix without applying the tool-input 256-node/16-KiB limit to the entire configuration. Unknown/hidden keys, accessors and malformed collections remain refused; ordinary tool inputs retain core's unchanged bounds. Duplicate agents, repository IDs or workspace bindings are rejected. Increment `policy.revision` for changes; the canonical hash includes the complete non-secret configuration, including App/installation/binding IDs. Configuration and issue assignment are re-read immediately before secret resolution and each data read; cache entries are policy/principal/run/issue/request scoped.

## Identity lanes

Each agent binding must explicitly select `identityLane: "app"`, the default and only implemented credential lane. Each tool and each enabled policy profile declares its allowed lane in code; `none` allows no lane. `owner` is a reserved name, not a second credential path: selecting it is refused with `identity.owner_disabled` before secret resolution or HTTP, even for an otherwise permitted read. Missing/unknown lanes and caller-supplied lane arguments fail closed. No owner secret is accepted or resolved, and there is no fallback between identities. The selected lane is part of the canonical configuration hash and every cache key. The reserved owner lane is prepare-only in the future: an exact payload plus hash, posted only by an authorized operator after the public-post gate. No owner credential may be bound until a separately accepted UID/sandbox boundary exists; fork pushes belong to that same gated lane, with no bot-attribution workaround.

Future write-tool requirements (not implemented or authorized here): hard-deny `APPROVE` reviews, required-context status/check creation, workflow-file writes and all workflow mint permissions regardless of profile. PR creation must flag or deny changes to `REVIEW.md`, `AGENTS.md`, `CLAUDE.md` and `.devin/`. Merge is release-profile only, with an agent independent of the PR author who verifies every rejected finding. Do not post bot commands to Devin or Dependabot; no bot-trigger or required-check bypass is allowed. App Git Data commits must omit custom author/committer/signature fields, with a truthful DCO sign-off only where required.

The future App-authored PR canary must record actual Actions, PR standards, CodeQL applicability, Devin status producer, CodeRabbit, Sourcery and cubic behavior, not assume advisory enrollment. Operator installation also adds the broker bot login to the upstream watcher's `ourLogins`; this plugin never changes watcher configuration.

## Credential, transport and rate behavior

The shared GitHub package adapts the existing upstream watcher's RS256 construction and fixed GitHub-origin REST mechanics. It intentionally drops its unscoped mint and credential cache. Every uncached call signs at call time, mints with exactly one `repository_ids` entry and only the endpoint's read `permissions`, verifies the returned repository/permission envelope, and revokes the installation token in `finally`. Metadata read is GitHub's implicit base permission. Token expiry must be future and no later than 61 minutes after call start (one-hour GitHub TTL plus one-minute clock/transport tolerance). Credentials are never placed in tool output, logs, plugin state, files, environment variables or child processes. There is no promise of managed-memory zeroization.

The native host's HTTP bridge transiently handles authorization headers and responses in memory; it must not trace or persist them. Source inspection of host 2026.1023.0 found a single DNS-pinned `node:https` request with no redirect following, a 5-second DNS deadline and 30-second request deadline. The SDK drops `redirect`/`signal`: this package does **not** pretend those ignored options enforce safety. The host buffers at most 200 MiB before IPC; the broker rejects bodies above 1 MiB, projects allowlisted fields, caps each projected page at 256 KiB and redacts known credential strings (including decoded base64 file contents). Reverify host behavior, telemetry and gateway mapping in sandbox acceptance, especially after upgrades.

Required mitigated behavior per worker: four concurrent calls, 30 attempted authorized calls per agent/minute, 4,000 reserved HTTP requests per installation/hour (including mint, repository verification, reads, revoke and up to two cleanup probes), and at most 128 entries in each bounded map. Reserve `N+5` before secret access. GitHub `Retry-After`/rate-reset signals pause that installation without in-run sleep or retry. Only projected, scrubbed data is cached for 10 seconds, never tokens or ETags for revalidation; fresh hits still recheck authorization. Each config/issue/workspace/secret/audit await and each HTTP mint/read/revoke/probe (including response-body consumption) shares a 30-second worker deadline and the same worker-wide four-operation IPC budget with at most four FIFO waiters. The deadline includes queue time and abandons the await, not the underlying host operation: its slot remains occupied until known settlement. The pinned SDK's non-TIMEOUT `JsonRpcCallError` is an explicit completed host error response and releases accounting without implying call success. Its locally constructed TIMEOUT error and generic ambiguous rejections prove no native settlement; they permanently quarantine that reservation in this worker. A late fulfilled result releases accounting only; an ambiguous late rejection does not. The two-second recovery window bounds worker dispatch/observation, not host DNS/network lifetime or a hard whole-call deadline. No caller cancellation/deadline is serialized as supported SDK behavior. Saturated/detached admission can refuse HTTP cleanup as well as audit; failed revocation still pauses minting even when the visible result is `audit.unavailable`. Provider expiry remains the fallback for an unrevoked token. An unauditable call fails closed. A permanently stalled host therefore requires Operator recovery rather than unbounded detached work. Installation reservations are keyed by App/installation across companies and use the clock at reservation time. The agent bucket counts admission attempts, not a strict rolling limit on physical HTTP start times; delayed calls can cross fixed windows. Provider backoff retains the maximum deadline. Rate state and caches reset on worker restart; GitHub remains the authoritative cross-worker rate enforcement. These are abuse/backpressure controls, not a billed-spend guarantee or a durable distributed quota.

## Install and rollback runbook

1. Do **not** install until the mitigation is implemented, exact-artifact/config/host Security and independent cryptography acceptance, exact-head Actions checks and required Devin Review/finding dispositions are recorded. Include the actual run-scoped REST caller in that review, then obtain Release Manager production approval and authorized Operator execution. REST does not repair MCP; a fixed MCP bridge is not a prerequisite to the REST acceptance path.
2. Use the dispatch-only **Package GitHub broker** Actions workflow (`.github/workflows/package-github-broker.yml`) after its recipe is independently reviewed. Dispatch from the exact reviewed **workflow revision**, passing the full reviewed, merged **source SHA** as `source_sha`. These are separate identities: a historical source commit cannot supply a workflow added later. The workflow checks out each separately. Build source is pinned literally to `5e32d7ae9f7d057318229db6fcd5894d4b6bf3e4`; `source_sha` only confirms that pin, never selects arbitrary code. This source adds bounded cleanup-probe diagnostics; it does not establish live cleanup reliability or authorize re-enablement. The earlier `2b0c7cc97c6c515af7ed14e7c347a167b6bf0337` candidate is not selected by this recipe. A different source requires a reviewed recipe change. It refuses a mismatched/non-full SHA or source outside merged `main` ancestry, runs the packaging verifier fixtures from the recipe checkout, runs `npm ci --ignore-scripts` and `npm test` on the source, verifies tracked inputs are unchanged, then runs script-free `npm pack` on `plugins/github-broker`. The recipe fixtures need no npm install and run on every packaging dispatch; the historical source suite alone does not cover them. This builds the independently installable package's transitive core/GitHub sources and REST client. No local full-suite run or host packing is required or authorized.
   - The 14-day Actions artifact contains the `.tgz`, `package-lock.json`, `dist-manifest.json` (sorted relative dist paths with per-file SHA-256), `build-evidence.json` (source/tree, recipe/script/workflow hashes, Node/npm versions, SDK version/resolved URL/lock integrity and run/attempt), and `SHA256SUMS`. Its step summary prints the package digest, all evidence digests and artifact URL. The upload archive's digest is **not** the npm package digest.
   - Before upload, every tar member must byte-match the tested dist or allowlisted package metadata. Missing worker/client/manifest entries, unexpected files, duplicate/traversal paths, links, changed bytes and oversized packages fail closed. No archive is extracted or installed by this job; no credential, publication or runtime change is involved.
   - Retain the exact run/job/artifact links and package/evidence digests before expiry, and independently verify `SHA256SUMS` before any authorized preparation. Artifacts are candidates, not Security/Crypto acceptance or permission to install. The target host's actual SDK resolution, effective configuration hash and capability/telemetry evidence remain separate acceptance prerequisites; the build's installed SDK version does not prove the worker's loader path.
3. The Operator installs the reviewed plugin artifact and grants only its manifest capabilities. They bind the approved company's App private-key secret and board-only App/installation IDs and versioned profiles. Bind only the approved narrow read-capable App and verified installation. No broad interim App is permitted; this runbook grants no exception or credential creation authority.
4. After authorized installation, QA verifies native plugin governance and audit coverage on the target host, secret/worker isolation, an unconfigured-policy denial, a cross-repo denial with zero upstream calls, and successful sandbox-only reads. Confirm all eight tools in `GET /api/plugins/tools` and separately record fresh-session discovery, including `repo_read` and `rulesets_get`; a flat-schema fixture is not live inventory evidence. On the approved REST caller path, verify each intended caller's company/agent/run/task binding, workspace/repository scope, profile denial, approval/rate gates and gateway invocation audit. Verify both a parseable policy denial with a nonzero client exit and an uncached successful sandbox read with zero exit. Do not test mismatched principals by borrowing another caller's credential. Missing MCP projection is recorded separately, not used to block REST acceptance. Record credential-free evidence for the relevant cleanup and cache paths:
   - An uncached sandbox read must show upstream 200 and either a real DELETE 204 (`revoked`) or the exact typed SDK failure followed by one qualifying 401, or valid-ID first 200 followed by the single bounded qualifying second 401 (`revoked_verified_by_probe`). On the pinned SDK, record the fallback's null DELETE request ID, `sdk_null_body` reason and valid probe request ID, not an invented 204. Confirm no cleanup pause on verified cleanup; a fresh cache hit does not test revocation.
   - Repeat identical arguments/principal/run/policy within 10 seconds to check the authorization-checked fresh cache, then after 10 seconds (allowing for transport latency) to check a new unconditional 200 read and cleanup. Confirm **no `If-None-Match`** is sent even if the provider supplies an ETag. There is no 10–60-second revalidation window and no requirement to obtain a live 304.
   - Run live canary steps sequentially; abort the sequence on the first cleanup failure or other stop condition. Have the Operator disable first and preserve the candidate/pause and only allowlisted audit evidence. Retain ordered `probes`, `secondDispatched`, `terminalReason`, legacy `probeStatus`/`probeResult`, available sanitized request IDs and the event/run/config correlation; report null/unavailable evidence as such. Do not batch further reads into the pause, replay a retained token, restart to clear the pause, infer revocation lag from the SDK error, or re-enable without renewed exact-envelope authorization. Diagnostic source changes alone are not operational acceptance.
   - CI regressions must cover the normal 204 path, strict first-probe fallback and bounded second-probe recovery and negative status/body/request-ID/throw cases, pre-secret `N+5` reservation, monotonic deadline/late-result refusal and uncertain-slot quarantine past SDK timeout, no revalidation, unsolicited 304 fail-closed, and no cache publication/minting after unverified cleanup. Do not induce those failures with unauthorized live credentials.
   - A well-formed REST envelope alone is insufficient: actual per-caller authorization, nested failure propagation, native governance/audit and successful uncached cleanup evidence are required. Missing any of those leaves the sandbox canary pending. These instructions are not an execution or acceptance record.
   - Retire the REST client only after a containing stable release is installed and QA verifies fresh-session MCP non-null structured output, correct tool-error propagation and the same authorization/sandbox canary. Then switch callers back to MCP and delete this temporary client and its route-specific fixtures/runbook. SDK revoke-fallback retirement is a separate gate.
5. Disable the plugin to roll back; remove its secret binding and revoke the App key/installation tokens through authorized operator controls if needed. Do not remove other connectors/grants. A revoke failure reports failure, clears cached results and pauses new minting for the maximum token lifetime in the current worker. A process crash/ambiguous mint may leave only GitHub's server-enforced expiry; see residual risks.

REA angle: reuse the shipped watcher's JWT/HTTP protocol and the existing test-environment plugin's authoritative issue/assignee/project checks, with core closed schemas and hash/dispatch primitives. No host/core patch or new credential launcher is introduced.
