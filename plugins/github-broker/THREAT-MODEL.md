# GitHub read broker threat model

Version 0.1.0; status **pending independent Security and cryptography acceptance**. This is not an installation approval. SDK/host baseline 2026.1023.0, REST 2022-11-28, core 0.1.0, shared GitHub 0.1.0.

## Assets, principals and boundaries

Assets: the company-secret App RSA key, signed JWT, scoped installation token, private repository content, trustworthy policy/audit and the shared GitHub installation rate budget. A compromised key inherits the App's **whole configured ceiling**, not merely this plugin's reads. The broker's mint ceiling is metadata plus contents, pull requests, issues, checks, statuses and Actions **read**. The separately configured App ceiling was reported narrowed on 2026-11-06: workflows none; Actions/checks/statuses read; contents/pull requests/issues/discussions write; remaining granted permissions read. Those residual App-level writes are not available through this broker's explicit read-only mint allowlist, but remain part of key-compromise impact; exact installation permissions must be verified at acceptance. Ruleset GETs require only metadata read; administration is excluded from the mint allowlist. No workflow, secret, organization-member, environment or write permission is requested by minting. A broader App key is not made intrinsically narrow by this broker and is unapproved absent explicit independent acceptance.

The authenticated gateway supplies company/agent/run/project identity. Tool selectors are untrusted. Policy comes only from board configuration. The host issues/projects APIs resolve current company, project, assignee, checkout/execution run, active status and selected workspace; the workspace URL must exactly equal board configuration. Numeric repository scope is enforced both at mint and by an ID verification read. Native host authorization, gateway provenance, company isolation and config-write controls are dependencies, not reimplemented authority. The plugin has no task mutation, checkout, database, filesystem, shell, scheduler or plugin-state capability.

The credential-bearing worker and host HTTP bridge are trusted processes, **not an OS sandbox**. A same-user host/process compromise or alternate credential-readable filesystem path defeats this trust model; this plugin does not remediate host credential isolation. No other provider's secret is bound here.

## Temporary REST caller boundary

`src/client.ts` uses only the runtime's existing run bearer at the fixed `/api/plugins/tools/execute` agent route, with the fixed plugin key and the eight registered reads. It resolves no App secret or installation token. Its process environment/API origin is trusted; an environment-controlling attacker already controls that process's bearer. TLS is required except for loopback HTTP. Redirects, URL credentials/query/fragment, non-root/API base paths, board/non-run key shapes, identity overrides, cross-task/workspace selectors, unknown tools/arguments and arbitrary transport destinations are refused. Local JWT decoding is only a structural mismatch/expiry check: the server's signature verification and live company/agent/run/project validation remain the authority. Project UUID is explicit caller metadata verified by the server, not a client grant.

The caller reuses existing closed schemas/path validation; stdin caps at 16 KiB/5 seconds, the single POST and body share a 45-second abort deadline and 1-MiB body cap. No retry, confirmation/idempotency override, gateway-session creation or persisted client state. An abort is not server cancellation. The broker's rate, audit, scope, cleanup, `N+4`, pause and cache controls are unchanged. HTTP status/reason codes and approval references remain failures; a parseable envelope alone is not read success. The exact plugin/tool wrapper, data boolean outcome and successful operation/repository must match. Nested SDK errors or denial data fail even on HTTP 200; null/replay summaries and ambiguous shapes fail closed. Only projected data and bounded error metadata are returned, with run-bearer reflections scrubbed from serialized keys and values; raw exception/host error text is discarded.

Baseline host 2026.1023.0's REST gateway still records the wrapper as succeeded despite nested plugin errors; caller failure propagation does not repair that native invocation row. Broker activity outcome remains independent evidence and must be correlated with native policy/invocation audit at acceptance. The baseline automatic approved-action executor rejects plugins with `approved_execution_unsupported`; never interpret approval as completed execution or resend a confirmation flag. The client preserves approval references and stops. These shipped limitations, gateway redaction/audit durability and actual per-caller authorization need exact-host Security/Crypto and QA acceptance, not a client-fixture claim.

Retire the client only after a containing stable host release is installed and QA verifies MCP structured data, nested errors and equivalent caller/sandbox controls. No runtime fork or upstream merge is required to accept REST. This retirement is independent of the SDK revoke-probe retirement below.

Inventory scope: `packages/github/src/index.ts`, all eight modules under `plugins/github-broker/src/tools`, and the repository-ID read in `src/broker.ts`. Every upstream URL is fixed to `https://api.github.com`; redirects never become authority to change destination. The probe below is the temporary cleanup mitigation. This source-derived inventory is not runtime acceptance.

### Null-body status caveats

The pre-mitigation baseline sent `If-None-Match` on retained ETags and accepted 304 for tool reads; those exposures must be removed, not authorized by the mitigation. Under the temporary contract, no GET sends `If-None-Match` or revalidates an ETag; only the 10-second fresh, authorization-checked projected-data cache remains. An unsolicited 304 fails closed whether the SDK throws reconstructing it or a future transport preserves its status. No endpoint has an accepted 205 success path. A 204/205 from a JSON endpoint is unexpected and must not become an empty successful projection. The SDK RPC fixture's synthetic DELETE 205/304 cases are defect controls, not additional GitHub endpoints or accepted DELETE outcomes. The shared request helper accepts no ETag option. Its path parameter does not authorize an arbitrary endpoint or generic null-body workaround.

This inventory is source-derived, not a live enumeration of every status GitHub could emit or proof of host behavior. All normal data responses require JSON and projection validation; errors and redirects do not gain a success interpretation. No GraphQL, combined `/status`, comments, blob/download, logs, artifacts or additional authentication endpoint is called by these modules.

Each tool has its own module and exact registry/manifest declaration. Unknown names (including prototype names), unknown keys, malformed shapes, unsupported enums, identities, Unicode/control/path ambiguities and out-of-range/fractional/coerced values are denied. Core schema limits bound overall input depth, nodes and bytes. Discovery schemas are flat root objects for MCP-client compatibility; they deliberately cannot express every mode-specific required/forbidden combination. Closed runtime variants still enforce those combinations before secret resolution or HTTP, as tested in `test/discovery.test.mjs`. Tool metadata is marked read-only; that label is not proof of native MCP governance coverage.

## Confused deputy and revocation

Every call resolves its issue server-side; assignee alone is insufficient, so either authoritative checkoutRunId or executionRunId must match the gateway's run. A different issue assigned to the same agent is not an automatic alternate audience. Closed tasks, foreign project/workspace/repository, unknown agents and `none` profiles deny before secret resolution. No caller-supplied token/secret/header/base URL/approval flag is recognized.

Configuration hash, assignment and workspace binding are revalidated before secret resolution, after mint and before each data read. Scoped tokens independently prevent a rename/transfer/TOCTOU from opening a second repository. Any policy change invalidates cache keys; assignment is checked even for fresh cache hits. Remaining same-repository timing races do not widen permission/resource scope. There is no claim of an atomic transaction across board policy and GitHub.

Each tool and policy profile declares its identity lane independently of its operation/repository scope. Agent policy must explicitly select `app`; the reserved `owner` lane is disabled before credential resolution or HTTP. Caller arguments cannot select a lane. There is no owner-secret configuration or fallback path. Lane changes alter the policy hash and invalidate caches; revalidation repeats the lane checks before each read.

### Temporary revocation verification boundary

On pinned SDK `2026.1023.0`, the plugin transport will match **only** a `TypeError` with the exact message `Response constructor: Invalid response status code 204`, for **only** `DELETE https://api.github.com/installation/token`. It will expose a typed failure to shared cleanup, with no fake status/response/header. Other methods, URLs, thrown types/messages and 205/304 reconstruction failures cannot enter the fallback.

Shared token cleanup then attempts exactly one `GET https://api.github.com/installation/repositories?per_page=1`, using the identical token and the same `ctx.http.fetch` path, deadline and IPC budget. Only a 401 JSON object whose `message` equals `Bad credentials` plus a sanitized valid `x-github-request-id` establishes `revoked_verified_by_probe`. Valid IDs must match `^[A-F0-9]{4,8}(?::[A-F0-9]{2,12}){3,5}$` and remain unchanged by credential scrubbing. Missing, malformed or credential-bearing IDs are not evidence. A 200 means cleanup is unverified, not permission to reuse the token. All other statuses, malformed/non-object JSON, message mismatch, missing/invalid ID or throws retain `mint.revoke_failed`, clear the call's cached results, publish no pending cache updates and pause new minting until maximum token expiry in that worker. No probe retry, alternate HTTP path, remint or budget bypass is authorized. Audit failure remains fail-closed and must not suppress the cleanup pause.

This probe proves **token rejection at the time of the probe**, not causal proof that DELETE succeeded; expiry or independent revocation remain possible explanations. The normal path is a real DELETE 204, classified `revoked` without probing. Neither cleanup outcome alone implies overall tool success: policy, data projection and durable audit must also succeed. The fallback is an explicitly temporary weaker evidence path, not a repair of SDK response reconstruction or the host MCP result bridge.

Removal requires adoption of a compatible published SDK containing [upstream #17282](https://github.com/paperclipai/paperclip/pull/17282), evidence that the actual worker resolves it, a flipped real-RPC status/request-ID preservation regression, deletion of the fallback/probe-specific handling, and normal exact-head CI, independent Security/cryptography and installed-host acceptance. An upstream merge or dependency declaration alone is insufficient.

## Injection and credential escape

Repository/task/API content is inert data. No content determines authorization, scope, destination, secret choice or execution. Results are explicit projections, not raw bodies. Known key/JWT/token strings and PEM lines are removed from projected text; files are decoded before scrubbing; selected request-ID headers are grammar-checked and scrubbed before audit; the temporary mitigation must not retain ETags for revalidation. HTTP failures expose fixed rule codes, not request headers, response messages, stack traces or error causes. Credentials are never put in state, files, environment variables or subprocesses. Trusted in-memory transfers carry the RSA private key from the host secret service into the worker over secret-resolution IPC, then the worker signs the App JWT. The worker sends that JWT and the derived installation bearer token to the trusted native HTTPS host over HTTP-bridge IPC. The worker, both IPC paths and the host secret/HTTPS services are all inside the credential-exposure trust boundary.

Tests use generated synthetic RSA material and a distinctive installation-token canary, with success/error/decoded-file reflection. No real credentials are fixtures. Redaction is defense in depth, not a cryptographic proof against arbitrary adversarial transformations of secrets. Worker crashes, heap dumps, debugger access and unrelated same-user filesystem exposure remain host-level risks.

## Lifecycle, caps, audit and failure

No cloud resources or billable jobs are created. Provisioning ledgers, paid-spend reservations, resource teardown jobs and destructive approval consumption are therefore not applicable. Internal installation tokens are minted per uncached call and revoked in `finally`; returned scope and expiry are checked first. GitHub's one-hour token expiry (61-minute validation tolerance) is the independent automatic teardown after worker crash or ambiguous mint. No token is persisted for a restart-time sweep. All HTTP, including revocation, the possible single cleanup probe and response-body consumption, must share the native IPC budget and deadline under the temporary contract. Saturation or detached HTTP can therefore prevent revocation from starting; no cleanup exemption bypasses the host budget. Failed revocation is an error and pauses minting in that worker until maximum expiry; the Operator must investigate repeated cleanup failures. A restart resets this process-local pause. This limitation must be accepted explicitly, not described as durable revocation recovery.

Required mitigated bounds: four concurrent admitted broker calls, four active native IPC operations with at most four FIFO waiters sharing each call's 30-second deadline (no new waiter admission while any active IPC is detached), 30 calls/agent/minute, a conservative 4,000-request installation/hour reservation, bounded maps, explicit one-page reads, 1-MiB broker response limit, 256-KiB projected page cap, 128-KiB file cap and a 10-second fresh projected-data cache with authorization checked on hits. Reserve `N+4` **before secret resolution** for mint + repository-ID verification + `N` data reads + DELETE + possible one probe: seven requests for `checks_get`, five for other uncached tools. No `If-None-Match` or ETag revalidation; unsolicited 304 fails closed. No retries or sleeps. Native HTTP is DNS-pinned, single-request/no-follow, bounded by 5-second DNS and 30-second request timeouts and a 200-MiB host buffer; the smaller broker check occurs after that host buffering. Request budgets reset on restart and are not a durable quota across replicas; GitHub enforces the actual installation limit. No broad credential cache is retained.

An activity intent is emitted and acknowledged before secret access/mint; durability remains an exact-host acceptance requirement. Outcome/refusal records include event/time, available gateway principal/run/company, configuration policy hash/revision once parsed, repository ID, exact operation, decision/rule, safe GitHub request IDs and outcome. Pre-policy validation or unknown-tool refusals use `hash(null)` and null revision, with null identity/selectors where parsing never succeeded; they do not resolve configuration or credentials just to fill audit metadata. Under the temporary contract, add a separate `revocation` audit field: successful cleanup has `outcome: "revoked"` for real DELETE 204 or `outcome: "revoked_verified_by_probe"` for qualifying probe evidence. The fallback must have `deleteRequestId: null`, `unavailableReason: "sdk_null_body"` and the valid sanitized `probeRequestId`. Never infer the DELETE request ID from the probe or synthesize its status; normal cleanup records only actually available sanitized DELETE evidence. Unverified cleanup is still a failed call, not either successful cleanup outcome. The call-level `outcome` remains pending/success/error, independent of cleanup classification. No arbitrary args, probe body/error text or credentials are logged. Audit outage before mint prevents outbound traffic; post-read audit failure is an error, never unqualified success. GitHub reads are safe to repeat but minting is not blindly retried. Audit retention/integrity/access and native invocation audit must be verified at install; an activity API alone does not certify them.

## Acceptance and recovery

Kill switch: disable plugin, remove binding, and perform authorized key/token revocation if required. Existing grants/connectors stay intact. No production install, credential creation/rotation, security exception, host/core modification or write-tool authority is supplied by this source change. Required independent reviewers must assess the host IPC/logging, redirect contract, activity durability, governance, broad-key ceiling, ambiguous-mint/expiry and same-user isolation limits on the exact artifact. QA then verifies only an approved sandbox repository after Operator installation.

REA angle: existing GitHub App watcher signing/HTTP and test-env authoritative issue checks are studied and adapted; their unscoped mint, token-return contract and permissive parser behavior are expressly not reused.
