# Discord synthetic canary evidence validator

These modules validate **synthetic, source-derived fixtures offline**. They do not invoke Paperclip or Discord, read credentials, install a plugin, or establish that a live staging canary happened. The host envelope is modeled on Paperclip `d69631b01b9c658f80bf8bed389863dce82643e1`; broker payload and projections are modeled on agent-toolkit `4af09093d16e6ec5ec38c9f96fc30ecf7e39fbc3`. A future live qualification needs separate Security and exact-target Release Manager gates.

`validateSyntheticEvidence(envelopeBytes, auditBytes, expected)` accepts UTF-8 JSON byte arrays and an expected audit identity and guild/channel identity. It returns either `{ ok: true, evidence: "synthetic_source_derived" }` or `{ ok: false, reason: <fixed code> }`; it never returns supplied values. The outer envelope and nested serialized payload are independently parsed with a 128 KiB byte limit, depth limit of 12, and maximum 100 entries per array or object. Duplicate keys, unknown fields, errors, malformed projections, unexpected identities, duplicate message IDs, and ambiguous audit pairs fail closed. Numeric tokens must use integer syntax and be safe integers; fractional and exponent forms are rejected even when mathematically integral. These limits deliberately constrain accepted fixtures and are not assertions that every otherwise valid upstream response fits.

The synthetic audit input consists of exactly two wrappers with `pluginId`, numeric `sequence`, and `record`: intent then successful outcome. Expected event, operation, caller, run, company, policy hash and revision must match both records. Plugin identity and sequence are **caller-supplied wrapper assertions**, not authenticated broker audit fields; this validator cannot prove origin, uniqueness across captures, ordering by the actual host, or freshness across invocations. Duplicate message IDs are rejected within a page, but this stateless validator cannot detect replay across separate inputs. Do not treat success as live evidence or a replay-prevention guarantee.

The acceptance policy is narrower than the pinned broker's complete success surface. For example, it rejects missing required metadata, cross-channel or cross-guild message references, duplicate message IDs, and null pages (including the broker's 204 path), even when the broker could return them successfully. The broker audit record does not include request arguments: a matching pair cannot prove which channel was requested. These are fail-closed limitations, not claims about the upstream contract.

Fixtures and tests are under `test/canary-*.test.mjs`. They contain invented identifiers and no live response data. Avoid recording raw response values in failure messages or logs.
